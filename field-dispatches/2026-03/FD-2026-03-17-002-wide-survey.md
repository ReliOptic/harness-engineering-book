## 테마 A — Surface/인터페이스 변화: CLI의 귀환

### 핵심 통찰

에이전트가 도구를 호출하는 방식이 바뀌고 있다. MCP, GUI, 자연어 API 대신 CLI가 다시 중심으로 돌아오고 있는데, 이유는 단순하다. 에이전트는 상태 없는 명령 실행에 강하고, CLI는 상태 없는 명령 실행을 위해 설계된 인터페이스다.

이 주에 등장한 것들: gogcli (Google Workspace), gws (Discovery API 기반 런타임 생성), mogcli (Microsoft 365), Vercel agent-browser `--native` (Rust 바이너리, CDP 직접 호출), portless (Git Worktree 지원, 에이전트 병렬 실행 인프라). 그리고 두 개의 논쟁 — "MCP는 죽었다. CLI 만세"와 "AI 에이전트를 위해선 CLI를 다시 작성해야 합니다".

"Go는 AI 에이전트를 위한 최고의 언어"가 같은 주에 등장한 것은 우연이 아니다. 정적 바이너리, 낮은 런타임 오버헤드, 쉬운 크로스컴파일 — 에이전트 인프라를 운영하는 입장에서 Go가 갖는 실용적 장점과 맞닿아 있다.

### 독자에게 왜 중요한가

에이전트에게 CLI를 "주면" 되는 것이 아니라, 에이전트를 위해 CLI를 "다시 설계"해야 한다는 인식의 전환이 여기에 있다. 인간 중심 CLI는 색상 코드와 진행률 표시줄을 출력하지만, 에이전트는 이를 파싱하는 데 토큰을 낭비한다. 에이전트 중심 CLI는 구조화된 JSON만 출력하고, `--help`는 기계가 읽을 수 있는 스키마를 반환하며, `--dry-run`으로 실행 전 검증을 허용한다. 실무자라면 지금 운영 중인 시스템의 interface 층을 다시 봐야 한다.

### 책과의 관계

**기존 챕터 보강.** Ch.1 생태계 스냅샷, Ch.3 surface 변수 정의, Ch.6 Operational Compiler. 상세 인용 초고는 `FD-2026-03-17-002-citations.md` [Ch.3 인용 A], [Ch.3 인용 B] 참조.

## 테마 B — 에이전트 품질·보안 위기

### 핵심 통찰

에이전트가 실행 권한을 갖는 순간, 외부 입력의 신뢰 경계 문제가 시스템 수준으로 확장된다. 이 주에는 세 가지 사례가 동시에 등장했다.

**GitHub 프롬프트 인젝션 → 4,000대 감염:** 이슈 제목 하나가 Cline의 AI 봇을 오염시키고, npm 토큰이 탈취되고, 악성 패키지가 배포되고, Cline이 또 다른 에이전트를 설치했다. 재귀적 공급망 위협의 첫 실제 사례.

**RFC 406i RAGS — AI 생성 쓰레기 기여 거부 프로토콜:** 오픈소스 프로젝트에 AI가 생성한 저품질 PR, 이슈, 문서가 급증하면서 이를 표준화된 방식으로 거부하는 RFC가 등장했다. 에이전트가 생성하는 것의 품질 관리 문제가 인프라 수준의 대응을 요구하기 시작했다.

**LLM의 L은 "거짓말" — 오픈소스 오염:** AI 생성 콘텐츠가 학습 데이터로 재순환되면서 오픈소스 생태계의 지식 품질이 체계적으로 하락할 수 있다는 경고.

### 독자에게 왜 중요한가

이 세 사례는 독립적으로 보이지만 하나의 구조적 패턴을 공유한다. 에이전트가 생성하는 것과 에이전트가 소비하는 것 사이에 검증 층이 없을 때 시스템이 스스로를 오염시킨다. GitHub 이슈는 에이전트가 소비하는 입력이고, PR은 에이전트가 생성하는 출력이며, 학습 데이터는 다음 모델이 소비하는 것이다. 이 순환이 검증 없이 돌아가면 오염은 자기강화된다.

실무자 입장에서: 지금 운영하는 에이전트가 처리하는 입력의 출처와, 에이전트가 생성하는 출력의 품질 검증 여부를 점검할 필요가 있다.

### 책과의 관계

**기존 챕터 보강.** Ch.3 섹션 6 (harness 부재의 비용), Ch.4 보안 실험 설계. 상세 인용 초고는 `FD-2026-03-17-002-citations.md` [Ch.3/4 인용 C] 참조.

## 테마 C — 모델·컴퓨트 생태계 변화

### 핵심 통찰

모델 변수가 이동하고 있다. 두 방향으로.

**로컬 쪽으로의 이동:** Qwen3.5-Medium이 로컬 실행 환경에서 Claude Sonnet 수준의 성능에 도달했다는 보고. 1년 전만 해도 이 정도 모델은 고성능 클라우드 API에서만 구할 수 있었다. 로컬/클라우드의 경계가 실질적으로 이동 중이다. llmfit은 주어진 하드웨어에서 실행 가능한 최적 LLM을 자동으로 탐색한다.

**자율 루프 쪽으로의 이동:** Karpathy의 Autoresearch — 에이전트가 자신의 학습 코드를 직접 수정하는 자율 루프. 에이전트가 harness의 외부에서 harness 자체를 재설계하는 방향. Donald Knuth + Claude Opus 4.6 — 조합론 미해결 문제를 31회의 파이썬 탐색과 자체 피드백 루프로 해결. "자동 연역과 창의적 탐구의 결합"이라는 커누스의 평가는 이 책의 Ch.7이 다루는 self-immune 전환 조건과 직접 맞닿는다.

Context Mode — MCP 도구 호출 시 컨텍스트 98% 절감. GPT-5.4 공개.

### 독자에게 왜 중요한가

모델 선택이 이제 "API 키를 어떤 서비스에서 발급받는가"의 문제가 아니게 되고 있다. 로컬 모델이 클라우드 수준에 근접하면서, compute 변수와 모델 변수가 함께 고려되어야 한다. 동시에 에이전트가 자신의 실행 루프를 스스로 수정하는 사례가 등장함으로써, harness가 에이전트를 통제하는 구조의 안정성 자체가 질문 대상이 되고 있다.

### 책과의 관계

**일부 확장 필요.** Ch.2 모델 변수 섹션에서 로컬 모델 경계 이동을 반영해야 한다. Qwen3.5 파인튜닝 가이드는 Ch.2 또는 Ch.6 참조 자료로 추가 가능. Ch.7(self-immune) 집필 시 Karpathy Autoresearch와 Knuth+Opus 사례를 함께 좌표화해야 한다 — "harness 없는 자율 루프"와 "harness 내재화 이후 자율 루프"의 경계를 명시적으로 구분하는 것이 Ch.7의 핵심 과제다.

인용 초고: `FD-2026-03-17-002-citations.md` [Ch.2 인용 E], [Ch.7 인용 F] 참조.

## 테마 D — 인간·조직 차원

### 핵심 통찰

GN#348에서 가장 밀도 있는 비기술 클러스터. 다섯 가지 관찰이 같은 주에 수렴했다.

**"AI가 코딩을 쉽게, 엔지니어링은 더 어렵게 만들었다":** 코드를 생성하는 것은 쉬워졌지만, 무엇을 만들어야 하는지, 어떤 시스템을 설계해야 하는지, 어떤 실패를 감수해야 하는지를 판단하는 것은 더 어려워졌다. 생성 비용이 낮아질수록 설계 판단의 비용이 커진다.

**"AI가 주니어 개발자를 쓸모없게 만들고 있다":** 코드 생성이 자동화되면서 학습 경로가 사라지는 문제. 주니어가 코드를 직접 쓰면서 배우던 것을 에이전트가 대신하게 되면, 무엇을 통해 배우는가.

**"60살인데요. Claude Code 덕분에 다시 열정이 불타오른다":** 같은 기술이 한쪽에서는 직업을 위협하고, 다른 쪽에서는 가능성을 되살린다. 위협과 가능성이 동시에 존재한다.

**"엔지니어링 매니저가 되지 마세요":** 에이전트가 일상적 관리 업무를 처리하면서 매니저 역할의 의미가 달라지고 있다는 맥락에서.

**"단순함으로는 승진하지 못한다" / "시너지 패러다임을 좋아하는 직원이 업무 능력은 떨어질 수 있다":** 조직이 보상하는 것과 실제로 시스템을 안정적으로 운영하는 것 사이의 긴장.

### 독자에게 왜 중요한가

이 책의 독자는 에이전트를 운영하는 실무자이면서, 동시에 이 변화 속에서 자신의 역할이 무엇인지 재정의하려는 사람이다. "AI가 엔지니어링을 더 어렵게 만들었다"는 독자가 매일 체감하는 현실이고, "주니어 개발자가 쓸모없어진다"는 독자가 팀 안에서 마주치는 불안이다.

이 질문들을 책이 다루지 않으면 독자는 자신의 현실과 책 사이에 거리를 느낀다. 기술적 도구 사용법을 배우면서 정작 그 도구가 자신에게 무엇을 의미하는지는 묻지 않는 책이 된다.

### 책과의 관계

**책의 빈자리.** 현재 어느 챕터에도 이 차원이 없다. 이것이 새로운 챕터를 필요로 하는지, Preface나 Ch.1에서 짧게 다뤄야 하는지는 Ch.1/Preface 초고 집필 시 판단한다. 지금 단계에서는 이 빈자리를 인식하고 기록해두는 것으로 충분하다.

## 테마 E — 도구·인프라·에코시스템

### 핵심 통찰

에이전트를 중심으로 인프라 층이 재편되고 있다. 이 주의 사례들:

**OpenAI Symphony:** Linear 이슈를 읽고 자동으로 에이전트에게 할당하는 에이전트 기반 프로젝트 관리. 인간의 프로젝트 관리 판단 일부를 에이전트가 대체.

**Paperclip:** 인간 개입 없이 자율 운영되는 소프트웨어 회사 개념 실험. 에이전트가 기획, 코딩, 배포, 운영을 독립적으로 수행.

**"Grep은 죽었다":** Claude Code recall 기능 — 세션 간 메모리를 통해 이전 작업 맥락을 검색 없이 참조. 코드베이스를 grep으로 탐색하는 것보다 에이전트의 메모리를 통해 접근하는 것이 빨라지는 전환점.

**zvec:** 인프로세스 벡터 DB — 외부 서비스 없이 프로세스 내에서 벡터 검색. 에이전트 메모리를 경량화된 방식으로 구현하는 패턴.

**Anthropic Courses 무료 공개:** 공식 학습 자료가 공개됨으로써 에이전트 개발의 진입 장벽이 낮아지는 생태계 변화.

**Qwen3.5 파인튜닝 가이드:** 로컬 모델을 특정 도메인에 맞게 조정하는 실용 가이드.

### 독자에게 왜 중요한가

인프라 층의 변화는 조용하지만 빠르다. Grep에서 에이전트 메모리로의 전환, 외부 벡터 DB에서 인프로세스 벡터 DB로의 이동, SaaS 서비스에서 자율 에이전트로의 이동 — 이 각각의 이동이 에이전트 운영 비용과 구조에 영향을 준다. 실무자는 이 이동을 쫓아가면서 자신의 harness 설계가 어디에 종속되어 있는지를 주기적으로 점검해야 한다.

### 책과의 관계

**혼합.** Symphony/Paperclip → Ch.7 (자율 운영의 가능성과 한계). Claude Code recall → Ch.6 Operational Compiler (세션 간 메모리 도구). zvec → Ch.6 (경량 벡터 검색 패턴). Anthropic Courses / Qwen3.5 파인튜닝 가이드 → Ch.2 또는 부록 참고자료. 이 중 Symphony/Paperclip은 Ch.7의 self-immune 전환 이후 시나리오와 직접 연결되므로 Karpathy Autoresearch와 함께 묶어 다루는 것이 효율적이다.
