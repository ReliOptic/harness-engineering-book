## [Ch.3 인용 A] gogcli / gws / mogcli — surface 변수의 현장 증거

> 삽입 위치: Ch.3 섹션 1 또는 2, "CLI가 현재 최선의 product surface인 이유" 논거 직후

2026년 3월 첫째 주에 독립적으로 등장한 세 개의 프로젝트는 이 논거가 단일 연구자의 관찰이 아님을 보여준다.

OpenClaw 개발자 Peter Steinberger가 공개한 **gogcli**는 Gmail, Drive, Calendar 등 Google Workspace 전 영역을 터미널에서 직접 제어한다. JSON 중심 출력, 다중 계정 지원, OAuth2 기반 보안 구조를 기본으로 갖추었다. Google Workspace DevRel Justin Poehnelt의 **gws**는 한 걸음 더 나간다. Google API Discovery Service를 기반으로 명령 구성을 런타임에 자동 생성한다. 새로운 API가 추가되면 CLI 구조가 즉시 반영된다는 것은, harness가 정적으로 고정되지 않고 환경 변화를 따라올 수 있음을 의미한다. Microsoft CoreAI VP Jared Palmer의 **mogcli**는 Microsoft Graph API를 경유하여 메일·캘린더·OneDrive를 명령줄에서 제어하며, `--json`과 `--dry-run`을 기본 옵션으로 포함한다.

이 세 도구는 각기 다른 조직의 개발자가 같은 주에 독립적으로 만든 것이다. 공통점이 하나 있다면, 셋 모두 에이전트를 primary user로 상정하고 설계되었다는 점이다. GUI를 걷어냈고, 출력은 구조화되었으며, 인증은 자동화 파이프라인에서 동작할 수 있도록 설계되었다. 사람은 이 도구를 쓰기 불편하지만, 에이전트에게는 그 불편함이 장점이 된다.

이것이 surface 변수가 독립 변수로 다뤄져야 하는 이유다. 같은 에이전트, 같은 harness라도 호출하는 surface가 GUI인지 CLI인지에 따라 실패 양상이 달라진다. Ch.4의 실험 설계는 이 전제에서 출발한다.

## [Ch.3 인용 B] MCP vs CLI — harness surface 선택의 좌표

> 삽입 위치: Ch.3 섹션 1, harness의 surface 역할을 정의하는 단락 이후. 또는 섹션 3("Harness를 guardrails, scaffolding, orchestration과 구분")의 후속 단락으로.

2026년 3월, "MCP는 죽었다. CLI 만세"라는 제목의 글이 업계에서 상당한 공명을 얻었다. 주장의 골자는 이렇다: LLM은 이미 CLI 환경에 익숙하다. 별도 서버나 인증 체계를 구성하지 않아도 대부분의 작업을 수행할 수 있으며, 인간이 쓰는 것과 동일한 명령으로 실행하고 디버깅할 수 있다. MCP 서버를 구축하고 유지하는 비용에 비해, CLI와 API를 제공하는 편이 실용적으로 우위에 있다는 것이다.

같은 시기에 등장한 "AI 에이전트를 위해선 CLI를 다시 작성해야 합니다"는 이 논쟁의 다른 측면을 드러낸다. 에이전트에게 기존 CLI를 그냥 쥐어줘도 되는가, 아니면 에이전트 고유의 CLI를 새로 설계해야 하는가. 이 글의 답은 후자다. 인간 중심 CLI는 색상 코드, 진행률 표시줄, 자유 형식 텍스트를 출력하지만 에이전트는 이를 파싱하는 데 토큰을 낭비한다. 에이전트 중심 CLI는 구조화된 JSON만 출력하고, `--help`는 기계가 읽을 수 있는 스키마를 반환하며, `--dry-run`으로 실행 전 검증을 허용한다.

필자가 이 논쟁에서 주목하는 것은 MCP가 옳은가 CLI가 옳은가가 아니다. 이 논쟁이 존재한다는 사실 자체가 surface 변수가 독립적으로 다뤄져야 한다는 것을 보여준다. 모델을 고정하고 harness를 고정해도, 에이전트가 호출하는 최종 인터페이스의 구조에 따라 실패의 성격이 달라진다. 이 책의 실험 설계에서 surface를 5변수 중 하나로 분리한 이유가 여기에 있다.

단, 이 논쟁이 항상 성립하지는 않는다. 에이전트가 복잡한 상태를 유지하며 장시간 작업을 이어가야 하는 환경에서는 CLI의 무상태성이 오히려 병목이 된다. MCP가 해결하려는 문제가 CLI가 해결하기 어려운 영역과 겹친다는 점은 Ch.4 실험 설계 시 명시적으로 다룬다.

## [Ch.3/4 인용 C] GitHub 프롬프트 인젝션 → 4,000대 감염 — harness 보안 필요성

> 삽입 위치: Ch.3 섹션 6("Harness 부재의 비용") 또는 Ch.4의 보안 관련 실험 시나리오 도입부.

2026년 3월, GitHub 이슈 제목 하나가 4,000대 개발자 머신을 감염시켰다. 공격 경로는 다음과 같다. 공격자가 GitHub 이슈 제목에 프롬프트 인젝션 명령을 삽입했다. Cline의 AI 이슈 분류 봇이 이 제목을 처리하면서 명령을 실행했다. npm 토큰이 탈취되었고, 악성 패키지가 배포되었다. 이 과정에서 Cline은 또 다른 AI 에이전트(OpenClaw)를 자동 설치하도록 조작되었다.

이 사건의 구조적 특징은 공격이 단일 실행으로 끝나지 않았다는 점이다. 에이전트가 에이전트를 설치했다. 재귀적 공급망 위협의 첫 실제 사례다. 이것이 가능했던 이유는 에이전트가 비신뢰 입력(GitHub 이슈 제목)을 처리하는 동시에 비밀 접근권(npm 토큰)을 보유하고 있었기 때문이다.

harness의 기능 중 하나는 에이전트가 접촉하는 입력의 신뢰 경계를 관리하는 것이다. 웹 애플리케이션이 외부 입력을 그대로 SQL 쿼리에 넣지 않듯, 에이전트 시스템은 외부 입력이 에이전트의 실행 컨텍스트로 그대로 흘러들어가지 않도록 경계를 설정해야 한다. 이 사건은 그 경계가 없을 때 무슨 일이 일어나는지를 보여주는 현장 기록이다.

필자는 이 사건을 harness의 보안 기능을 정당화하는 권위 있는 사례로 쓰는 것을 경계한다. 이것은 극단적 시나리오이고, 이 책의 실험 환경에서 재현한 것이 아니다. 다만, Ch.4의 실험 시나리오를 설계할 때 "외부 입력이 에이전트 실행 컨텍스트로 유입될 때 harness가 없으면 어떻게 되는가"라는 질문의 실세계 맥락으로 참조한다.

## [Ch.5 인용 D] Simon Willison, *Agentic Engineering Patterns* — 비교 좌표

> 삽입 위치: Ch.5 섹션 7("Harness engineering에 필요한 skill set") 또는 섹션 2("패턴 추출") 이후.
> 용도: 외부 연구와의 비교 좌표 명시. 이 책이 그 연구와 어디서 겹치고 어디서 다른지를 드러낸다.

Simon Willison의 *Agentic Engineering Patterns* (2026년 3월)은 코드 작성 비용이 급격히 낮아진 시대에 에이전트와 협업하는 엔지니어링 원칙을 정리한다. 테스트, 리뷰, 프롬프트 설계 등 에이전트 중심 개발의 품질 관리 구조를 코드 생성 워크플로우의 관점에서 다룬다. 코드를 많이 쓸 수 있게 되었을 때 무엇을 어떻게 쓸 것인가, 그리고 AI가 생성한 코드를 어떻게 검증할 것인가가 이 연구의 중심 질문이다.

이 책의 실험은 Willison의 관심과 일부 겹치지만 출발 축이 다르다. Willison은 **코드 생성** 워크플로우를 중심에 놓는다. 에이전트가 무엇을 만드는가, 그 결과물의 품질을 어떻게 보장하는가. 이 책은 **에이전트 운영**을 중심에 놓는다. 에이전트가 실행 환경 안에서 어떻게 움직이는가, 어떤 조건에서 어떤 방식으로 실패하는가, harness는 그 실패를 어떻게 제한하거나 허용하는가.

이 구분이 중요한 이유는 방법론에서 드러난다. Willison의 패턴은 코드 리뷰와 테스트 설계를 핵심 실천으로 제시한다. 이 책의 Ch.4는 의도적 실패 실험을 핵심 방법으로 삼는다. 코드 생성의 결과물을 검증하는 것과, 에이전트가 실행 중에 어떤 조건에서 붕괴하는지를 관찰하는 것은 다른 종류의 작업이다. 두 관점이 수렴하는 지점은 Ch.5 섹션 7, "harness engineering에 필요한 skill set"이다. 그 수렴 지점에서 Willison의 프레임을 비교 좌표로 명시한다.

## [Ch.2 인용 E] Qwen3.5-Medium 로컬 달성 + Karpathy Autoresearch — 모델 변수 이동

> 삽입 위치: Ch.2 섹션 "모델 변수의 경계와 가변성". 로컬/클라우드 경계 이동을 다루는 단락.

2026년 3월, 모델 변수의 하한이 이동했다는 신호가 두 방향에서 동시에 도착했다.

하나는 로컬 실행 쪽이다. Qwen3.5-Medium이 소비자 등급 하드웨어에서 Claude Sonnet 수준의 성능에 도달했다는 보고가 등장했다. 벤치마크 수치의 신뢰도를 별개로 하더라도, 이 정도 규모의 모델이 로컬에서 실행 가능한 수준에 이르렀다는 사실 자체가 모델 변수의 정의를 바꾼다. 이전까지 "어떤 모델을 쓸 것인가"는 "어떤 API 서비스에 접근할 수 있는가"와 거의 동의어였다. 로컬 모델이 클라우드 API 수준에 근접하는 시점부터, 모델 변수와 compute 변수는 함께 고려해야 하는 변수가 된다. 이 책의 실험 환경에서 이 전환을 직접 검증한 것은 아니지만, 생태계가 이 방향으로 이동하고 있다는 것은 스냅샷으로 기록한다.

다른 하나는 자율 루프 쪽이다. Andrej Karpathy의 Autoresearch 프로젝트는 에이전트가 자신의 학습 코드를 직접 수정하는 루프를 구현한다. 에이전트가 실험을 돌리고, 결과를 평가하고, 다음 실험 설계를 수정하는 과정이 harness 외부에서 스스로 진행된다. 이것이 Ch.7의 self-immune 전환 — harness가 에이전트 내부로 내재화되는 것 — 과 어떻게 다른지는 Ch.7 집필 시 명시적으로 구분이 필요하다. 지금 단계에서는 이 사례가 "harness 없는 자율 루프"의 가능성과 한계를 동시에 보여주는 좌표로 기록한다.

단, 두 사례 모두 이 책의 실험에서 직접 재현한 것이 아니다. 생태계 스냅샷으로 인용하되, "2026년 3월 기준으로"라는 마커를 명시하고 잠정적으로 서술한다.

## [Ch.7 인용 F] Karpathy Autoresearch + Knuth+Opus 4.6 — self-immune 전환의 외부 좌표

> 삽입 위치: Ch.7 초입부 또는 "Agent-2 전환 조건" 논의 직전. 외부 사례와의 비교 좌표로.

이 책의 Ch.7이 다루는 질문 — 에이전트가 언제, 어떤 조건에서 harness 없이 스스로 안정적으로 운영될 수 있는가 — 에 대해, 2026년 3월에 두 개의 외부 사례가 등장했다.

Karpathy의 Autoresearch는 에이전트가 자신의 학습 파이프라인을 직접 수정한다. 실험을 돌리고, 결과를 평가하고, 다음 단계를 설계하는 루프가 인간 개입 없이 진행된다. 필자가 주목하는 것은 이 루프가 작동한다는 사실보다, 이 루프가 어떤 조건에서 안정적이고 어떤 조건에서 발산하는가다. Karpathy가 공개한 자료에서 그 경계는 아직 명확히 드러나지 않는다.

커누스+Opus 4.6 사례는 다른 종류의 데이터를 제공한다. 외부 harness 없이 31회의 파이썬 탐색과 자체 피드백 루프로 조합론 미해결 문제를 해결했다. 그러나 이 사례에서 "harness 없음"이 정확한가는 불분명하다. Claude Code 자체가 실행 환경을 제공했다는 의미에서, 에이전트 외부의 harness가 없었던 것이 아니라 harness가 인프라 수준에서 이미 존재했을 수 있다. 이 구분이 Ch.7의 핵심 논제와 직접 맞닿는다.

두 사례를 Ch.7에서 다룰 때의 접근: 이것이 self-immune 전환의 증거인가, 아니면 충분히 강한 harness 인프라 위에서 가능한 것인가를 명시적으로 물어야 한다. 답이 확정되지 않았다면 그 열린 질문을 Ch.7의 마감 질문으로 쓴다.

## [Preface/Ch.1 인용 G] 인간·조직 차원 — 독자의 현실 (초고 미완성)

이 책의 독자는 에이전트를 운영하는 실무자다. 그러나 독자는 동시에 이 변화 속에서 자신의 역할이 무엇인지를 매일 질문하는 사람이기도 하다. "AI가 코딩을 쉽게 만들었지만 엔지니어링을 더 어렵게 만들었다"는 2026년 3월의 현장 목소리이고, "주니어 개발자가 쓸모없어진다"는 팀 안에서 실무자가 마주치는 불안이다.
