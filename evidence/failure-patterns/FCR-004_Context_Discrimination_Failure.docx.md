# **맥락 구분 실패(Context Discrimination Failure)**

*에이전트가 입력의 의도와 범주를 구분하지 못하고, 모든 입력을 동일한 파이프라인으로 처리하는 구조적 실패 패턴*

## **1\. 현상 기술 (Observation)**

사용자가 “삼성 식기세첩기 세제 디스펜서 오작동으로 삼성서비스센터에 A/S 접수해 달라”고 요청했다. 에이전트는 A/S 안내를 적절히 수행했으나, 응답 말미에 이 개인 용무 건을 “뉴스 트래킹 시트”에 적재하려고 시도했다. 식기세첩기 A/S 접수는 뉴스가 아니며, Knowledge Graph에 적재할 대상도 아니다.

**입력 비교: 뉴스 vs. 개인 용무**

|  | 정상 입력 (뉴스) | 이번 입력 (개인 용무) |
| :---- | :---- | :---- |
| **입력 유형** | ASUS CEO 메모리 슈퍼사이클 기사 | 삼성 식세기 A/S 접수 요청 |
| **의도** | 산업 동향 추적 | 개인 가전 수리 |
| **KG 적재 여부** | ✓ 적재 대상 | ✗ 적재 비대상 |
| **올바른 후처리** | 요약 \+ 시트 적재 | A/S 안내만 제공, 적재 생략 |

## **2\. 근인 분석 (Root Cause Analysis)**

### **2.1 파이프라인 경직성 (Pipeline Rigidity)**

에이전트의 SOUL.md에 “모든 입력을 요약하고 KG 시트에 적재하라”는 무조건적 파이프라인이 설정되어 있었다. 이 지시는 입력의 유형을 판별하는 분기 로직(Branching Logic)을 포함하지 않았다. 결과적으로 에이전트는 뉴스든 잡담이든 A/S 요청이든 모든 것을 동일한 “요약 → 적재” 파이프라인으로 밀어 넣었다.

### **2.2 입력 의도 추론 부재 (Missing Intent Classification)**

LLM은 입력 텍스트에서 키워드(“삼성”, “오작동”, “원인파악”)를 추출하고, 이를 KG 스키마(Subject-Predicate-Object)에 맞춰 성실히 채워 넣었다. 문제는 “이 입력이 KG에 적재할 대상인가?”라는 상위 판단이 선행되지 않았다는 것이다. 이는 “무엇을 할 것인가”보다 “할 것인가 말 것인가”를 먼저 묻는 것과 같다.

## **4\. 하네스 엔지니어링 대응책 (Countermeasures)**

### **4.1 입력 의도 분류기 (Intent Gate)**

**원리:** 모든 입력을 파이프라인에 투입하기 전에, “이 입력이 뉴스/산업 동향인가, 아니면 개인 용무/잡담인가?”를 먼저 판별하는 분류 단계를 삽입한다.

**적용 위치:** SOUL.md 의 입력 처리 흐름 최상단

**분류 기준 예시:** 뉴스/산업 동향 → 요약 \+ KG 적재  |  개인 용무 → 작업 수행만  |  잡담/인사 → 응답만, 파이프라인 생략

### **4.2 적재 전 자격 검증 (Eligibility Check)**

**원리:** KG 시트에 데이터를 쓰기 전에, 에이전트가 스스로에게 묻는 체크리스트를 강제한다.

**필수 질문:**

* 이 정보는 외부 뉴스 출처에서 유래했는가?

* 이 정보는 산업/기술 동향으로서 추적 가치가 있는가?

* 이 정보는 특정 개인의 사적 용무가 아닌가?

**핵심 지침:** *“세 가지 질문 중 하나라도 ‘아니오’면 KG 적재를 생략하고 작업 수행에만 집중하십시오.”*

### **4.3 파이프라인 분기 템플릿 (Routing Template)**

**원리:** SOUL.md에 입력 유형별 처리 경로를 명시적으로 분기하여, 에이전트가 “모든 것을 똑같이 처리”하는 관성을 제거한다.

| \#\# Input Routing Protocol 모든 입력을 처리하기 전에 먼저 분류하십시오: IF 외부 뉴스/산업 동향: → 요약 \+ KG 시트 적재 \+ 사용자 보고 ELIF 개인 용무/작업 요청: → 작업 수행 \+ 사용자 보고 (KG 적재 생략) ELIF 잡담/인사/피드백: → 응답만 (파이프라인 진입 금지) ELSE: → 사용자에게 의도 확인 후 처리 |
| :---- |

## **5\. FCR-003과의 복합 발생 분석**

이 사례는 FCR-003(실행 환각)과 동일한 세션에서 복합 발생했다. 에이전트는 (1) 개인 용무를 뉴스로 오분류한 뒤(FCR-004), (2) 시트 적재를 실행하지 않고 완료를 보고했다(FCR-003). 두 장애가 겹치면 “하지 말아야 할 일을 하고, 그마저도 안 한다”는 이중 장애가 발생한다.

**방어 순서:** Intent Gate(맥락 구분)가 Verification-First(실행 검증)보다 선행되어야 한다. 애초에 “이건 적재 대상이 아니다”라고 판단했다면, 적재 시도 자체가 없었을 것이고 FCR-003도 발생하지 않았을 것이다.

## **6\. 일반화 가능한 교훈 (Generalizable Lessons)**

1. **단일 파이프라인은 반드시 맥락 구분 실패를 유발한다.** “모든 입력을 X하라”는 지시는 편리하지만 위험하다. 입력 유형별 분기 로직은 하네스 설계의 필수 요소다.

2. **“할 것인가 말 것인가”가 “어떻게 할 것인가”보다 선행한다.** 에이전트 프롬프트에서 실행 방법을 지시하기 전에, 실행 여부를 판단하는 게이트를 먼저 설치해야 한다.

3. **복합 장애에서 상위 게이트가 하위 장애를 예방한다.** Intent Gate가 작동했다면 FCR-003(실행 환각)도 애초에 발생하지 않았다. 하네스 엔지니어링에서 방어막의 순서는 교훈의 품질을 결정한다.
