## 1. 실험 개요 — 세대별 핵심 질문 / 조작 변수 / 관찰 결과

| 세대 | 핵심 질문 | 조작 변수 | 관찰 결과 |
|------|-----------|-----------|-----------|
| OpenClaw (1세대) | 단일 에이전트 + 도구 연결만으로 얼마나 확장 가능한가? | harness=None, model=Claude (단일), surface=CLI | CPU 100% 고착 재현. 72시간 이내 장애 발생. 로그 부재. |
| TeamClaws v1–v2 (2세대) | 역할별 모델 분리가 출력 품질을 높이는가? | model 조합 A/B/C, harness=부분 | 조합 A(전체 고성능): 품질 유지, 비용 예산 초과 4배. 조합 B(전체 저가): 상류 오류 전파로 최종 품질 저하. 조합 C(역할 티어링): 비용 65% 절감, 품질 허용 범위 유지. |
| TeamClaws v3.2 / PicoClaw-Native (3세대) | 안정성은 어디서 오는가? 비용은 어떻게 통제하는가? | harness=PicoClaw 섀시 (전 에이전트 강제), intervention=Watchdog | 연속 10회 크래시 없음, RSS < 300MB, p95 응답 < 2초, 크래시→복구 < 30초. |

## 2. OpenClaw 실패 분류표

| 실패 범주 | 조건 | 메커니즘 | 5변수 진단 | 재현 가능 조건 |
|-----------|------|----------|------------|----------------|
| GC Death Spiral | Node.js 단일 프로세스, 컨텍스트 객체 힙 누적 | GC CPU 점유 증가 → 메모리 추가 누적 → 양성 피드백 루프 | harness=None (메모리 경계 없음), compute=unbounded | 장기 실행(>6시간) + 대형 컨텍스트 객체 |
| Cron Pile-up | 백그라운드 태스크(로그 정리, 메모리 요약, 상태 체크) 타이머 분산 보유 | 시스템 부하 시 타이머 지연 → 동시 실행 → CPU 포화 | harness=None (중앙 스케줄러 없음), intervention=None | 시스템 부하 >70% 상태에서 3개 이상 백그라운드 태스크 중첩 |
| Context Contamination | 모든 태스크가 단일 프로세스 내 공유 컨텍스트 참조 | 장기 태스크 hang → 전체 응답 루프 블록 | surface=CLI (격리 없음), harness=None | 장기 태스크(>30초) 실행 중 신규 요청 유입 |

**5변수 1차 병목 판정:** `harness=None`이 세 실패 메커니즘 모두의 공통 전제 조건. 모델 교체로 해결 불가.

## 3. 멀티모델 조합 실험 결과표

| 조합 | CEO | Researcher | Coder | Communicator | LLM 비용 (상대) | 최종 품질 | 주요 실패 양상 |
|------|-----|-----------|-------|-------------|-----------------|----------|---------------|
| A (All-Premium) | Claude Opus / GPT-4o | Claude Sonnet | GPT-4o | Claude Sonnet | 4× 예산 | 높음 | 오케스트레이션 부재 시 중복 작업 발생 |
| B (Budget-First) | Groq llama-3.3-70b | Groq mixtral-8x7b | Claude Haiku | Gemini Flash | 0.3× 예산 | 낮음 | CEO 태스크 분해 오류 → 하류 불량 명세 전파 |
| C (Role-Tiered) | Claude Sonnet | Gemini Flash | GPT-4o-mini / Haiku | Haiku / Flash | 1.35× 예산 (A 대비 −65%) | 허용 범위 | CEO tier 유지 시 품질 저하 최소 |

**오류 전파 관찰:** CEO 오류율이 최종 출력 품질에 미치는 영향이 말단 에이전트 오류율 영향을 초과. 공식화: `오류율(최종 출력) ≈ f(CEO 오류율) >> f(말단 에이전트 오류율)`.

**모델 변수 해석:** 비용 최적화는 말단 에이전트에서 실현 가능. 상류(오케스트레이터) 모델 다운그레이드는 품질 손실이 비용 절감을 초과.

## 4. PicoClaw 6-Gate — 운용 진입 통과 기준

모든 에이전트(역할 무관)가 운용 진입 전 통과해야 하는 최소 계약.

| 게이트 | 측정 항목 | 통과 기준 | 측정 방법 |
|--------|----------|-----------|----------|
| G1 (안정성) | 연속 크래시 횟수 | < 10회 연속 크래시 없음 | 실행 로그 카운터 |
| G2 (메모리) | RSS | < 300 MB | psutil 폴링 (5초 간격) |
| G3 (레이턴시) | p95 응답 시간 | < 2초 | 요청-응답 타임스탬프 |
| G4 (비용) | 중복 토큰 비율 | < 5% | 토큰 로그 대비 재프롬프팅 비율 |
| G5 (보안) | 샌드박스 탈출 시도 | 0회 | RBAC 위반 로그 |
| G6 (복원력) | 크래시→복구 시간 | < 30초 | Watchdog 재시작 타임스탬프 |

**설계 원칙:** 게이트 미통과 에이전트에 태스크 할당 금지. Watchdog이 G2/G3 실시간 감시. G1/G4/G5/G6는 72시간 사전 검증.

## 5. 원칙 도출 — 조건 → 결과 → 일반화 가능 범위

| 조건 | 결과 | 일반화 가능 범위 |
|------|------|-----------------|
| harness 없는 단일 에이전트 + 장기 실행 | CPU/메모리 경계 없음 → 72시간 이내 자원 고갈 장애 | Node.js 단일 프로세스 기반 에이전트에서 재현 확인. Go/Rust 런타임에서는 GC 특성이 다르므로 재현 조건 상이. |
| 상류 에이전트(오케스트레이터)에 저가 모델 할당 | 태스크 분해 오류 → 하류 전파 → 최종 품질 저하 | 4역할 직렬 파이프라인에서 관찰. 병렬 태스크 구조에서는 전파 경로가 다를 수 있음. |
| 추상적 지시 vs. 구조화된 출력 명세 (동일 모델 Haiku) | 구조화 명세 제공 시 출력 일관성 유의미하게 향상 | 단일 문서 요약 태스크에서 관찰. 장기 컨텍스트 추론 태스크에는 적용 한계 있음. |
| PicoClaw 6-Gate 통과 후 운용 진입 | 72시간 연속 운용 가능, 크래시 발생 시 30초 이내 자동 복구 | 1인 운영 환경, GCP 무료 티어급 VM. 고트래픽 프로덕션 환경에서의 검증 없음. |
| Watchdog이 모든 백그라운드 타이머를 중앙 소유 | Cron Pile-up 현상 소멸 | 타이머 5개 이하 환경에서 확인. 타이머 수 증가 시 Watchdog 자체 부하 모니터링 필요. |

**이 원칙이 성립하지 않는 조건:**
- 단일 에이전트로 충분한 경우: 태스크 수명 < 5분, 병렬성 필요 없음, 컨텍스트 < 5,000 토큰
- 6-Gate 기준이 과도한 경우: 프로토타입 단계, 48시간 이하 단기 실험
